## Decisions & Context

- **The CSS half of WS6 is impossible as specified — do NOT retry.** Astro's CSS
  plugin walks `importers` CONCAT `dynamicImporters`
  (`node_modules/astro/dist/core/build/graph.js`), so a lazy chunk's stylesheet is
  hoisted back onto every page that can reach it. Measured: `fp1-tune` was a
  byte-identical no-op (same content hash) and `lenis-tune` shipped **twice**
  (bundled copy stayed, inline `<style>` copy added), costing **+329/+439/+380 b
  gz**. The only working technique is `?url` + a runtime `<link>`, but ClientRouter's
  head swap then strips it and it would need an `astro:after-swap` re-assert in all
  three panels — not worth ~200 b gz on dev-only benches.
- **Stage 4 is a LATENCY win, not a bytes win.** A visitor who plays video
  downloads the same total (`/work/bedouin` is +0.9 kb gz overall). 157 kb simply
  stopped blocking hydration; it now rides in parallel afterward. Do not quote
  Stage 4 as a payload reduction.
- **The bench split is worth ~1 kb, not the estimated 4–9 kb.** The panel chunks
  import their tune-state libs back out of the eager parents
  (`LenisTunePanel` → `SiteShell`, etc.), so only the React UI moved.
  `src/lib/lenisTune.js` and friends stayed eager.
- **A failed hls chunk fetch is TERMINAL for the document.** ESM module-map
  semantics: a rejected dynamic import is cached, so every later
  `import('hls.js')` rejects from cache without a network request. The first
  implementation had a retry that looked right and did nothing; a reviewer proved
  it against the real build. Degrades correctly (native HLS where available, else
  poster, no crash) but the live tier parks at `pending` until reload. Commented
  in the file.
- **Safari precedence unchanged.** The codebase deliberately prefers hls.js on ALL
  browsers including Safari, because `preferMinQuality`/`preferMaxQuality` need
  rendition control. WebKit was verified to take the MSE path (`src=blob:`), not
  native. A Safari carve-out would silently change globe-panel and Lightbox quality.
- **Reduced motion is a bonus win:** `VideoGlobe.jsx:82` and `WorldScene.jsx:38`
  gate `VideoSlotPool` out of the tree entirely, so under reduced motion the hls
  chunk is never even fetched. The 4 "no video" matrix cells assert
  `videos===0` AND a clean console, so a regression would flip them to
  `UNEXPECTED-VIDEO`.
- **`/process` is prod-gated** (`process.astro:25` redirects unless DEV) to a
  274-byte HTML, so its bench split is dev-hygiene only, not a shipped saving.
- **Lightbox is unreachable on the running site** — its only mount is
  `ProjectDirectory` on `/work/directory`, which `directory.astro:25` redirects
  away unconditionally for v1. The verifier mounted it by hand to test the
  `preferMaxQuality` path. Worth knowing before anyone "fixes" a Lightbox bug.
- **PLAYWRIGHT GOTCHA (cost an agent ~30 min):** playwright-core 1.55's DEFAULT
  chromium (`chromium-1187` / `chromium_headless_shell-1187`) is built WITHOUT
  proprietary codecs — `MediaSource.isTypeSupported('video/mp4;codecs="avc1.42E01E"')`
  is false, so hls.js attaches MSE, buffers nothing, and every surface reads as
  dead. **Pin `chromium_headless_shell-1228`.** Use playwright-core at
  `~/.npm/_npx/e41f203b7505f1fb/node_modules/playwright-core` (v1.55.0; its
  expected `webkit-2203` IS installed). The copy in `/tmp/pw-verify/node_modules`
  is a broken partial install.
- **Session workflow (Nathan's standing directive) paid off again:** implementation
  subagents per workstream + adversarial review subagents. The bundle reviewer

  `chunkgraph.mjs` was blind to inline `<style>` blocks and had reported it as a
