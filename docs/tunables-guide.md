## How tunables work

**Everything is a URL query param, read on the client.** `?key=value` on the
page URL. Values parse with `parseFloat` / `Number`; anything non-finite falls
back to the default, so a typo is a silent no-op. Enum params compare exactly
(`?fillmode=Panels` ≠ `panels`). The server never reads them (`PARAMS` is null
during SSR), so SSR output is always the baked default.

**Three read-timing classes decide whether your param "took":**

| class | when it is read | consequence |
|---|---|---|
| module-load | once, when the JS module first evaluates (worldConfig, heroConfig, processConfig, enterTune, textExit, fp1Tune, footerTune, RouteFill, CtaArrows, WorldCard, NextProjectBand, DeckScroller, touchTune, `?scroll` in FeaturedProjects) | Put the param on the URL you **hard-load**. The Astro ClientRouter keeps modules alive across soft navs and drops the query string, so a param added after load, or on a link you clicked to, does nothing until a full reload. Conversely, a param on the first-loaded page persists through soft navs for the session. |
| mount-effect | each time the island mounts (panel gates `?deckdebug` `?entertune` `?texttune` `?pager` `?debug`, BandPager/GridSocket effects, `?lerp` `?wheelmult` `?lenisdur` per route) | Reflects the URL at mount time. SiteShell panels persist through soft navs because the shell is `transition:persist`. |
| per-render | `?detent`, `?wheeldetent` (TapeWheelPager reads them every render) | Live. |

**Gate styles differ.** Presence gates (`?deckdebug`, `?entertune`, `?texttune`,
`?debug`) accept any value, even `=0`. Strict gates need exactly `=1`:
`?herotune=1`, `?committune=1`, `?fp1tune=1`, `?lenistune=1`, `?footertune=1`.
`?pager` is an enum gate (`=tape`).

**Bench seeds are mostly always-on.** Hero, text-exit, footer, enter, World and
process knobs seed from the URL whether or not their panel is open, so a copied
`copy_url` previews the dialed values on a plain load. The exceptions: the fp1
shape knobs need `?fp1tune=1`, and raw Lenis knobs last one route (the bench
re-applies them).

**Two `copy_url` flavors.** hero/commit, enter, text, fp1, lenis and footer
start from the *current* search string (other params ride along), force their
gate, write only non-default values and delete defaulted keys. The deck-debug
and process panels rebuild from the pathname and **drop every other param**.

**Same key, different meaning on different routes.** `?scroll` (/work fill
threshold + footer reveal + home-return; detail next-project threshold;
/process legacy alias of `?swipepx`), `?scatter` and `?drift` (/work tile field
vs /process fragment belt), `?camlag` (/work and /process camera lag, same
default), `?debug` (VideoGlobe aside on `/`; ProcessDebugPanel on `/process`;
window globals on `/work`), `?deckhome` `?deckhold` `?deckalbum` (/work deck
panel vs the tabled detail BandPager). The route decides.

**Reduced motion** (`prefers-reduced-motion: reduce`) short-circuits most
motion knobs: no Lenis, instant Turns, no appear tweens, no enter ramp, no
pulse, no caret loop, no live-video pool, static deck walls, plain-link
next-project band. Panels still mount and `copy_url` still works.

**Bake law.** When a value is blessed, write it into the constant or token in
the `bake` column, then drop the param from your URL. Never leave a blessed
value living only in a `copy_url` link.

### Phone reading sections (SQ-26, reworked SQ-27, text fit + page end + top bounce + nav clearance SQ-28, 11-07; growth + air SQ-30, 11-08)

On a phone (≤768px) every description blurb, the intro and each later band, is its own **section 0.88 of the visible viewport tall once grown** (1 − the peek), its copy centred in the area below the pinned chrome (`project-detail.css`, `min-height` in `svh`; the top padding is `--blurb-clear`, the fixed nav plus the pinned breadcrumb chip plus a small gap, so a long blurb never starts under them). The page **seats** a section with its **top on the viewport's top**, so no media shows above it (the black section fills up under the nav) and the peek, 0.12 of the viewport (Nathan 11-08: 88%), of the next media shows below it. With a finger (`(max-width: 768px) and (pointer: coarse)`), the page **catches** there (a stop on the way in, no hold on the way out since SQ-68):

- **Arrival** is the driven footer's slowdown. The page's scroll velocity is tracked (native momentum, and the hold's own). For the next seat in the direction of travel, the page is taken when it is v/ω from the seat, where ω is Lenis's own λ (lerp × 60 per second) at the house lerp, the damp the footer's full reveal runs. A critically damped spring starts at exactly the page's speed (no velocity step) and never passes the seat, snapping within 0.5px. A page that comes to rest short of a seat, with a section covering half the viewport, is eased onto it from rest. A finger down is never taken mid-drag, and a new touch takes the page back; the lift decides. The section just left is not caught again until the direction reverses.
- **Stop, not a hold** (SQ-68, Nathan 11-12: "Toggle off the scroll tension when scrolling out of a text blurb area. Keep it on for as you scroll into a text area, for both scrolling down and up"). The tension is the arrival catch, kept in both directions: down into a blurb from the media above, up into one from the media below. Once a section is seated, the next gesture in either direction is the browser's own scroll, 1:1 from the finger's first move, with its own momentum: no `touch-action`, no `touchmove` listener, no rubber band, no dead zone, and the section just left is not caught again. A seat lands the way the page end does. `?blurbexit=1` brings back the old way out (the two bullets below), for a device compare.
- **Hold** (only with `?blurbexit=1`): the gesture on a seat is the house rubber band (`lib/rubberBand.js`, the same step the next-project band runs). The copy tracks the finger, the lift springs it home.
- **Exit** (only with `?blurbexit=1`) is natural momentum. A pull past the trigger (`SCROLL_TRIGGER_WORK_PX` of gained delta, 100px of finger at `TOUCH_GAIN` 5) commits: the page follows the finger 1:1 from there, then carries the finger's release velocity as momentum decaying at iOS's native rate (0.998 per ms, τ about 500ms, distance v·τ). No target, no fixed duration. The copy, offset by the band at the commit, eases home while the page carries, so neither it nor the media jumps. If that momentum reaches another section, the arrival applies to it. Both directions work.
- **Growth** (SQ-30, Nathan 11-08: "their vh grows to 88% tethered to the same motion curve as the scroll … only when scrolling into the text area from above or below, not when scrolling out of it"). With the hold running a section is its **content height** until it comes into view, so the next media sits right under it. From then on its `min-height` is written every frame from its position, so it follows whatever moves the page (finger, native momentum, the catch spring, the hold's own coast). It grows at its **bottom**: its top, the seat, never moves because of it. From below, progress runs 0 to 1 as the top travels from the viewport's bottom edge to the seat; from above, as the section's compact bottom edge reaches the top edge to the seat. Height = compact + (grown − compact) × progress, and the grown height is **(1 − peek) of `window.innerHeight`**, the VISIBLE viewport, sampled each frame while the section is still entering (svh reads about 78% with the iOS toolbars collapsed), never under the section's content. Progress only increases within an entry, so the section KEEPS its height leaving either way. Once it is fully **below** the viewport it goes back to compact at once (nothing visible moves). Once fully **above** it, it goes back only when the page is at rest (no finger, no scroll for 120ms, no catch, coast or carry), and the page is moved by exactly the height lost in the same task, because on iOS a programmatic scroll ends native momentum. `overflow-anchor: none` keeps Chrome from counter-scrolling the growth. A top section at scrollY 0, or one already in view when the hold attaches, starts grown by its position, with no load animation. Without the hold (no script, reduced motion, a narrow desktop window, `?blurbhold=0`) or with `?blurbgrow=0`, sections sit at their grown size (`min-height` 0.88 of `svh`).
- **Air above the copy** (SQ-30, Nathan 11-08: "a bit more empty black space at the top of the text area"). The copy is centred between the chrome clearance (`--blurb-clear`) and the section's bottom, and the top padding is `--blurb-clear` plus `--blurb-air` (`?blurbair`), so the copy never starts closer than that to the chrome. As a section grows, half the growth lands above the copy, so it eases down toward centre with the scroll. The text fit measures with that padding in, so the copy always fits the grown window at its worst case, 0.88 of the small viewport.
- A section taller than its seat window (more than 0.88 of the viewport, long copy on a short phone) is seated at its top and read with native scroll, not held.
- A blurb's keyword wipe plays when its section seats, when the page rests with it on screen, and when the page opens with it on screen.
- **Text size, fitted** (SQ-28, Nathan: "increase the size of the description text on mobile"). The detail blurbs' copy is `--text-blurb` (shared with the menu, tagline and pill, so it is not touched) times `--blurb-text`, one number per page, written to `.project-detail` by `blurbHold.js attachBlurbFit`. The number is the target (`?blurbtext`, 1.25 proposed) or the largest scale under it at which every blurb on the page still fits its seat window (0.88 of the **small** viewport, the padding with the air in, a `100svh` probe, so the hold works in either iOS toolbar state), measured by the copy's own height with the section's `min-height` lifted, including the nav clearance. Height grows roughly with the square of the scale (lines rewrap), so it measures, re-guesses and measures again, at most three times, and finishes on a scale that measured as fitting. The floor is 1 (today's size): a blurb that does not fit even there is read natively, as before, and it holds the rest of its page at 1. It re-fits when the width or the small viewport changes (an orientation turn, not an iOS toolbar sliding) and when the fonts land; the hold off (`?blurbhold=0`) and reduced motion still get the fitted size. The server render is 1, so a fit only ever grows the copy.
- **Page end** (SQ-28, Nathan: "apply this slow down to the bottom of the detail page"). The document's end is the last arrival target, downward only: momentum heading for it (native, or the hold's own coast) is taken v/ω before it with the same velocity-continuous spring and lands exactly on it, no overshoot and no bounce. It is a stop, not a hold (no seat, no `touch-action`, no entrance); the next-project band owns the gesture there, as before. The rest ease never targets it, and a section seat the end clamps to counts as the end. `?blurbend=0` turns it off.
- **Top bounce** (SQ-28). Every scroll sample is clamped to the page before it is read as movement, so an iOS overscroll at either end never flips the direction, and the page's very top is a rest of its own: the rest ease never pulls a page that rests at the top onto the first section. (A 16:9 hero leaves the intro more than half the viewport, which is what the bounce's downward settle used to trip, on `heavy-house-society-branding-2026`.)

Desktop (≥769px) is untouched. Reduced motion keeps plain 0.88 sections with natural scroll, no hold, no growth. These read at mount, so reload after changing them.

## Regenerating this guide

The key inventory is machine-extracted; the prose is not. When a param is added, renamed or removed:

```sh
node scripts/tunables-keys.mjs                                   # every param key with its read sites
node scripts/tunables-keys.mjs --check                           # fails if a code key is missing from this doc
grep -rlE "URLSearchParams|searchParams|location\.search" src    # the reader files (26 on 2026-09-01, 30 on 2026-10-16, 32 on 2026-11-01)
node scripts/tunables-guide-html.mjs docs/tunables-guide.md out.html   # rebuild the navigable HTML (artifact) version
```

The extractor follows every idiom in use: `params.get/has('k')`, the `num()` / `PARAM()` / `qNum()` / `str()` helpers, `PARAM_KEYS` maps, `FOO_PARAM = 'k'` name constants, `[param, option]` pairs, `stateKey: ['k', reader]` tuple maps (popConfig) and `location.search.includes('k')`. A new reading style needs a new regex there. Known false positives it ignores: `a`, `panels` (variant arrays), `equal`, `video`, `mix`, `shared` (popConfig vocab pairs), `email` (form field). For a new key, read its reader file and add a row: what it does, default with units, accepted values, bake target; if it is inert or dry-run only, say so in the lists above.
